# Installation, usability and data maintenance review

This review covered the three package definitions, installation and workflow
guides, CI, installed-package checks, and the library state, backup, restore and
locking boundaries. It used synthetic fixtures and temporary installations;
it is not a line-by-line audit of every audio algorithm or a live-library audit.

## Assessment

The package split is useful: Ableton inspection and hardware export remain
independent of the heavier analysis package. SQLite content identity, explicit
migration, operation journals, retained decisions and checksummed state bundles
provide a substantial foundation for long-lived data. Broad restructuring is not
justified by the findings in this pass.

Installation is still aimed at terminal users. A combined environment is the
clearest route through the complete workflow. Individual environments can run
their packages, but skip integration tests when another package is unavailable.
Documentation should keep the short setup path distinct from development and
optional model installation.

## Findings addressed

| Finding | Change and evidence |
|---|---|
| Malformed backup JSON objects or file records escaped as AttributeError, TypeError or KeyError. | Validate manifest and file-record shapes before restoration. Regression cases exercise preview and apply, require a structured error, and check that source evidence and destination parents are untouched. |
| Wheel checks preinstalled the entire development environment and used `--no-deps`, masking missing runtime declarations. | Fresh wheels now resolve declared dependencies under test constraints. Run the core smoke check before adding `review-ui`, then repeat with browser coverage. Add `pip check` to CI. |
| The library's `dev` extra omitted Flask although browser tests use it. Package installation examples also installed test extras unnecessarily. | Include Flask in `dev`; ordinary package examples install runtime requirements only. |
| Setup omitted cloning, editable-install consequences, installation verification and upgrade troubleshooting. | Expand Getting started, distinguish browser-only and model extras, and document supported/tested platforms. |
| Dependency ownership and the pinned snapshot update process were unclear. | Document `pyproject.toml` as authoritative and the fresh-environment update procedure. Clarify the legacy requirements placeholder. |
| Lifecycle details lacked a compact recurring maintenance routine. | Add backup destination guidance, restore layout, retention categories and the distinction between filesystem caches and cached data inside SQLite. Ignore `.eidetic/` in Git. |

## Remaining work, in priority order

**Follow-up, 9 September:** items 1 and 2 below have now been addressed for Python
3.12 on Apple Silicon macOS. The [AI setup](AI-SETUP.md) includes a hashed dependency
snapshot, offline real-model verification, resource controls and an opt-in CI job.
Library selection now requires `--root` or `SAMPLES_ROOT`; Ableton requires
`--root` or `ALS_ROOTS`. The earlier findings are retained below as review history.
The AI snapshot has not been validated on Intel Macs or Linux.

1. **Model reproducibility:** checkpoint revisions are pinned, but the optional
   PyTorch/Transformers/librosa environment is not. Establish a tested optional
   dependency snapshot with the two real-model checks before claiming reproducible
   classifier installation. The core snapshot is also not hash-verified and does
   not pin system FFmpeg or the build backend.
2. **Library selection:** several commands retain machine-specific fallback paths.
   Explicit `--root` and environment setup are documented, but a future deliberate
   CLI compatibility change could make first-run selection clearer. Do not silently
   change defaults that existing users may rely on.
3. **Shared state protocol:** export and library tools independently implement
   portable format and writer checks to avoid a heavyweight package dependency.
   Preserve cross-package integration coverage when either changes. Extracting a
   small shared protocol package would need a separate versioning and installation
   design; merging implementations casually would undermine their independence.
4. **Distribution readiness:** no software licence has been selected. That is an
   owner decision before broader distribution, not something this refactor should
   choose. Linux execution and hardware playback also need their own verification.
5. **Data growth:** maintenance provides visibility but no automatic retention or
   reconciliation of captured historical approvals. Keep its current evidence
   retention behaviour until a separately reviewed policy exists.

## Verification

- Combined source suite on Python 3.12/macOS: **696 passed, 2 skipped**. The skips
  are the explicitly enabled model-download integrations.
- The available library environment supplied test dependencies; `PYTHONPATH` added
  the sample and Ableton source packages for the combined run. The existing
  sample-tools environment lacked pytest; no Ableton environment was present.
- Built all three wheels and installed their declared base dependencies in a
  fresh temporary environment with the pinned snapshot used as constraints.
- Base installed-wheel smoke check passed outside the checkout, exercising command
  entry points, resources, onboarding, approval boundaries, FFmpeg export, changed
  mount paths, historical capture, backup and restore.
- Installed `review-ui` through its declared extra and repeated the wheel check:
  browser assets, write-token checks, shortlist playlist and packet handoff passed.
- `pip check`, `git diff --check`, compilation of the changed Python files, and
  the `.eidetic/` ignore-rule check passed.
- No real sample library, hardware profile, or preview/apply default was changed.

Remote CI, real model inference, instrument playback and the contents of the
user's live library remain outside this verification.
